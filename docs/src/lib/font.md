# `tairix-font` — shared text-rendering front end

`tairix-font` (`lib/font`) is the system's text-rendering front end. Font
rendering is one of the curated OS shared-library classes (`AGENTS.md` §16.4),
so it lives in `lib/*` and the taskbar, window manager, and default apps draw
text through it without depending on one another.

The crate holds **no font outline and no TrueType parser**. It holds two
things:

- a small compiled-in **console atlas** (`atlas`) with the Unicode glyph
  lookup over it (`glyph`), and
- behind the default-on `render` feature, a thin, cached **client** of the OS
  font service `fontd` (`client`) plus the blitter that draws onto a
  `lib/raster` `Surface` (`font`).

## The console atlas is the kernel/console subset only

The compiled-in atlas is the primary Inconsolata EX face's whole repertoire —
Latin, Greek, Cyrillic, box drawing, arrows, punctuation, currency, and
U+FFFD; 15×28 cells with 16-level anti-aliased coverage. It is generated by
`cargo xtask font-atlas --write` from the committed SIL OFL 1.1 face in
`lib/font/assets/`, so there is exactly one generator and one source of truth
(`AGENTS.md` §2.2).

Two consumers read the atlas and nothing else font-related:

- **The boot/headless text console** (`lib/fbcon`) links `tairix-font` with
  `default-features = false` (no `alloc`) and draws from the atlas *before any
  service exists* — it is boot floor (`AGENTS.md` §18.6). It therefore shows
  U+FFFD for a CJK or Hebrew scalar; rich CJK/Hebrew text is available through
  the graphical terminal, which draws via `fontd`.
- **The render client** reads the atlas's three monospace geometry constants
  (`atlas::CELL_WIDTH`/`CELL_HEIGHT`/`BASELINE`), so `BitmapFont`'s const-fn
  geometry stays local and no per-layout IPC is needed.

The CJK (Japanese, Korean) and Hebrew companion faces are **not** compiled in
anywhere. The full-Unicode atlas that older builds embedded into every consumer
(a ~3.6 MB payload, plus the four embedded TrueType faces at ~6.1 MB) is gone:
`/System/Fonts` holds only the four faces and `fontd` rasterises every size on
demand, so there is no second, precomputed atlas beside the faces it derives
from.

## Rendering goes through the sandboxed font service

With the `render` feature, `BitmapFont` is a thin, cached client of `fontd`
(see [the font service](../userland/fontd.md)). It parses no TrueType and holds
no face: `BitmapFont::draw_text` fetches each glyph's 8-bit coverage from the
service over `tairix_abi::font_ipc::FONT_ENDPOINT` and blits it through the one
shared `lib/raster` premultiplied-alpha path. Steady-state redraws issue no IPC
— each `(scalar, cell height)` reply is memoised in a bounded FIFO cache on the
client side.

The public API is unchanged from the pre-service crate, so consumers did not
change: `BitmapFont::inconsolata` renders at the native console size,
`BitmapFont::with_pixel_height` at any other size (the desktop resolves a
comfortable size from the theme's logical font size and the DPI scale), and
every metric scales with the cell height so the font stays monospaced.

### The transport is injected

`draw_text` takes no client handle, so the transport is a process-global,
`render`-gated seam behind a `FontTransport` trait:

- A program links the real transport with the `tairix-font/rt` feature, which
  routes each request through `tairix_rt::ipc_call(FONT_ENDPOINT, …)`.
- A host test installs a mock (`set_font_transport`, or the `test-util`
  `SolidTestTransport`), so the blitter is exercised with no service running
  and `lib/font`'s own host tests never pull `tairix-rt`.
- With **no** transport installed, a draw composites nothing and fails closed
  (`AGENTS.md` §5.4) rather than reaching for any local font data.

This mirrors how `lib/display` gates its `rt` transport non-default and lets
each consumer opt in, so the render libraries stay host-testable and the
headless build (`AGENTS.md` §17.3) is unaffected.
