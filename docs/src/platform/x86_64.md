# x86_64

This page describes the **Stage-2 QEMU integration test path** for x86_64.
Stage 3a will expand it into the full architecture port (UEFI boot, ACPI,
APIC, SMP, context switch, syscall entry).

## What is delivered today

`kernel/arch/x86_64` is a *partial* Stage-3a baseline. It exists because
the two Stage-2 deliverable integration tests — `memory_isolation` and
`scheduler_stress` — need an x86_64 boot path. Specifically, the crate
provides:

- **Two boot protocols into one 32→64 long-mode trampoline** (`boot.s`):
  a **multiboot2** header for real bootloaders (GRUB), and a **PVH**
  (`XEN_ELFNOTE_PHYS32_ENTRY`) note QEMU's `-kernel` ELF loader boots
  directly — the protocol every x86_64 QEMU integration test uses, with
  no firmware or bootloader in the loop. Both entries converge on the
  same trampoline; `entry.rs` validates the magic and records the
  protocol (`bootinfo`).
- A **-2 GiB higher-half kernel**. The kernel's Rust sections
  (`.text/.rodata/.data/.bss` and the AP-trampoline payload) are linked
  at virtual `KERNEL_VMA_BASE = 0xFFFFFFFF80000000 + phys` but loaded
  into low physical memory just above 1 MiB (`kernel/arch/x86_64/linker.ld`,
  matching the `-C code-model=kernel` build flag). Only the early
  trampoline (`.boot.*` — multiboot2 header, PVH note, 32-bit code, boot
  page tables, boot stack, early GDT) is linked 1:1 in low memory,
  because it runs with paging off. Running the kernel in the higher half is what
  lets the syscall-entry `RSP0` validator
  (`syscall_entry::validate_kernel_rsp0`) require a canonical higher-half
  kernel stack (ret2usr / CVE-2019-1125 hardening, AGENTS.md §5).
- Bootstrap paging that maps **both** the full 0–4 GiB physical window
  *identity* **and** the higher-half kernel window (`boot.s` + `paging`).
  The identity map is broadened from the original 0–32 MiB so the LAPIC
  MMIO frame at `0xFEE00000`, the IO-APIC frame at `0xFEC00000`, and any
  ACPI table the loader places below 4 GiB are reachable, and it backs the
  direct physical map (`kernel/mem` `phys.rs`) every DMA/MMIO access uses.
  The higher-half window (`PML4[511] → PDPT[510] →` the reused first-GiB
  identity PD) maps `0xFFFFFFFF80000000 + X` to physical `X`, covering
  the whole kernel image; the trampoline jumps into it with an absolute
  jump once long mode is on (`boot.s` SAFETY-INVARIANT 9). A kernel
  pointer is therefore converted to physical by `if v >= KERNEL_VMA_BASE
  { v - KERNEL_VMA_BASE } else { v }`.
- A minimal IDT for `#PF`, `#GP`, and `#DF` plus a closed-fail handler on
  every other vector (`idt`).
- A 16550 polled serial console on COM1 (`serial`).
- A QEMU `isa-debug-exit` helper (`qemu_exit`).

## Stage 3a (a) — platform discovery and APIC

Stage 3a (a) adds the *discovery* and *interrupt-controller* layer that
the remaining Stage 3a items (AP bring-up, context switch, syscall entry)
build on. Everything in this layer is `no_alloc` and host-unit-tested
behind MMIO / port-I/O traits so the same control flow runs under
`cargo test` as on real hardware.

| Module | Purpose |
|---|---|
| `multiboot2` | Zero-copy parser for the Multiboot2 information structure (tags 4, 6, 14, 15, 17). |
| `pvh` | Zero-copy parser for the PVH `hvm_start_info` record and its E820-style memory-map table. |
| `bootinfo` | Boot-protocol record (written once by `entry.rs`) + the protocol-neutral `BootData` view (`load`, `validated_rsdp`) every boot-info consumer dispatches through. |
| `pic` | Legacy 8259A quiesce (remap + mask-all), run by the boot stub so a BIOS-style hand-off (SeaBIOS/PVH, real legacy boot) can never deliver a legacy IRQ onto the exception vectors. |
| `acpi` | RSDP v1/v2 checksum validation; generic SDT header; typed MADT entry iterator (Local APIC, IO-APIC, Interrupt Source Override, LAPIC NMI, Address Override). |
| `apic` | LAPIC + IO-APIC drivers. Software-enable, EOI, INIT/SIPI IPI sequence, IO-APIC redirection-entry programming. MMIO is accessed through the `LapicMmio` / `IoApicMmio` traits; the production impl uses `read_volatile`/`write_volatile` and a single `// SAFETY:` block per accessor. |
| `apic_timer` | PIT-channel-2-calibrated LAPIC timer. Pure ticks-per-second/initial-count math is split out into `compute_initial_count` and `compute_pit_reload` and unit-tested independently. |
| `bootmemory` | Bridge from Multiboot2 / UEFI / PVH memory-map entries to `MemoryRegionDescriptor`s. A dev-dependency on `kernel/mem` powers a round-trip test that fails the build if the local `RegionKind` mirror ever drifts from `tairix_kernel_mem::RegionKind` (AGENTS.md §2.2 — no duplication). |

What is **not** delivered yet, and is tracked in `PLAN.md`'s Stage 3a
sub-checklist: context switch / interrupt entry–exit prologue (Stage
3a (c)), `syscall`/`sysret` entry, and full `kernel/core::KernelArch`
wiring.

## Stage 3a (b) — AP bring-up

Stage 3a (b) adds the application-processor (AP) startup path so
TAIRiX actually drives ≥ 4 emulated cores on QEMU. It is fully
exercised end-to-end by `tests/integration/scheduler_stress_qemu`.

| Piece | Source |
|---|---|
| Position-independent real-mode → long-mode payload | `kernel/arch/x86_64/src/ap_trampoline.s` |
| Trampoline installer + `ApBootSlot` + INIT-SIPI-SIPI sequencer | `kernel/arch/x86_64/src/smp.rs` |
| BSP-side orchestrator (boot info → ACPI → MADT → per-AP bring-up) | `tests/integration/scheduler_stress_qemu/src/kernel.rs` |

Key invariants (audited per AGENTS.md §10; each `unsafe` block carries a
`// SAFETY:` justification):

- The payload is assembled into a dedicated `.ap_trampoline` section of
  the kernel image and copied to the fixed 4 KiB-aligned low frame at
  `AP_TRAMPOLINE_PHYS = 0x8000` at boot. The SIPI vector is therefore
  `0x08`, decoded by `smp::sipi_vector()`.
- The trampoline transitions directly from real mode to IA-32e long mode
  per Intel SDM Vol 3A §10.8.5 (PE+PG set together in one MOV to CR0).
  Internal jumps use absolute offsets bound to `0x8000` so the payload
  can be copied verbatim from any link address.
- The AP reads its `ApBootSlot` (`cr3`, `stack_top`, `entry`, `cpu_id`)
  from a fixed in-page offset (`0xF00`) and `xchg`-releases a `ready`
  flag the BSP `Acquire`-loads before launching the next AP. The 4 KiB
  trampoline frame is therefore serial-reusable.
- The BSP and APs all run on the same `boot_pml4` (which maps both the
  identity 0–4 GiB window and the higher-half kernel window), so APs see
  the same memory map — and can run higher-half-linked entry code and
  stacks — without any per-AP page-table work in (b).

No preemption is wired in Stage 3a (b); cores execute cooperatively in
`Scheduler::step(cpu_id)` and observe spawned tasks on their next loop
iteration. LAPIC-timer-driven preemption is Stage 3a (c).

## Stage 3a (c) — per-CPU GDT + TSS + IST (partial)

Stage 3a (c) is being landed incrementally. The first slice introduces
the **per-CPU descriptor-table primitives** every CPU needs to replace
the trampoline-internal GDT (`ap_trampoline.s`) and the boot-time GDT
(`boot.s`) with a real long-mode descriptor table.

| Piece | Source |
|---|---|
| `GdtEntry`, `tss_descriptor`, `Tss`, `PerCpuGdt`, `Selectors`, `GdtPointer` | `kernel/arch/x86_64/src/gdt.rs` |

What the new `gdt` module provides:

- A 7-slot canonical GDT layout — null, kernel code, kernel data, user
  data, user code, plus the two 8-byte slots of a 64-bit TSS descriptor
  (Intel SDM Vol 3A §8.2.3 Figure 8-4). The user CS sits *after* user
  DS so an eventual `IA32_STAR` programming resolves `sysret` SS/CS
  correctly (SDM Vol 2B §SYSRET).
- A `Tss` struct laid out per SDM Vol 3A §8.7 Figure 8-11, with
  `RSP0`..`RSP2` privilege stacks and `IST1`..`IST7` interrupt stacks.
  The `iopb` field is parked one byte past the TSS so userspace
  `in`/`out` always `#GP` (no I/O permission bitmap).
- A builder API (`PerCpuGdt::set_ist`, `set_privilege_stack`,
  `finalize`) that validates every input — IST indices in `1..=7`,
  stack tops non-null and 16-byte aligned — and surfaces violations as
  `IstError` rather than panicking (AGENTS.md §2.9).
- A bare-metal `unsafe fn install(&'static mut self)` (gated behind
  `cfg(all(target_arch = "x86_64", target_os = "none"))`) that
  executes `lgdt`, reloads DS/ES/FS/GS/SS with the kernel data
  selector, reloads CS via a far return, and loads the TR with `ltr`.
  Every invariant the asm relies on (`'static` storage, finalized TSS
  descriptor, register clobbers) is documented in the `# Safety`
  block; the host unit tests below cover the non-asm portions
  exhaustively.

Host coverage (35 tests touching `gdt` directly):

- Every code/data descriptor's bit pattern is asserted against the SDM
  figures (`P`, `DPL`, `S`, `Type`, `L`).
- The 64-bit TSS descriptor splitter (`tss_descriptor`) is verified to
  scatter `base[0..64]` and `limit[0..20]` across the eight legacy
  fields, and to clamp a misuse-supplied `dpl > 3` rather than smear
  into the `P` bit.
- `Tss` field offsets are pinned via `offset_of!` against the SDM
  §8.7 figures (`RSP0=0x04`, `IST1=0x24`, `IOPB=0x66`,
  `size_of::<Tss>() == 0x68`); a separate `const _` assertion makes
  any struct edit that desyncs `TSS_BYTE_LEN` fail compilation.
- All four `IstError` paths are reached by negative tests.

### Stage 3a (c1) — per-CPU bring-up wired into the QEMU stress test

This slice integrates the `gdt` primitives above with the new
`interrupts` and `context` modules behind a single
`unsafe fn percpu::init(cpu_index)` entry point. Each CPU calls
`tairix_arch_x86_64::percpu::init` exactly once during bring-up.

| Piece | Source |
|---|---|
| `PerCpu` bundle (per-CPU GDT + IDT + IST stacks), `init`, `MAX_CPUS = 16`, `IST_STACK_BYTES = 16 KiB`, IST index constants | `kernel/arch/x86_64/src/percpu.rs` |

Properties:

- The arena is a single `static mut PER_CPU: [PerCpu; MAX_CPUS]` in
  `.bss`; no allocator is involved. `MAX_CPUS = 16` is the source of
  truth and is cross-asserted against
  `tests/integration/scheduler_stress_qemu/src/kernel.rs::MAX_CPUS` by
  a `const _: () = assert!(…)` in the test crate.
- IST 1 is reserved for `#DF` (Double Fault, vector 8), IST 2 for
  `#NMI` (vector 2); both stacks are 16 KiB and 16-byte aligned by
  virtue of `#[repr(C, align(16))]` on `PerCpu`.
- A per-CPU `AtomicBool` latch (`PER_CPU_INITIALISED`) makes a second
  call for the same index return `InitError::AlreadyInitialised`
  rather than re-installing a half-mutated table.
- After `init` returns the per-CPU GDT is `lgdt`-installed (CS/DS
  reloaded, `ltr` issued) and the per-CPU IDT is `lidt`-installed
  with every vector routed through the common ISR prologue
  (fail-closed by default).

The `scheduler_stress_qemu` integration test now calls
`percpu::init(0)` at the very top of `kernel_main` and
`percpu::init(cpu_id as usize)` at the very top of each AP's
`ap_entry`. The trampoline-internal GDT is therefore live only between
SIPI delivery and the AP's first Rust instruction; from then on each
AP is on its own real per-CPU descriptor tables.

### Stage 3a (c2) — common ISR prologue

| Piece | Source |
|---|---|
| `InterruptStackFrame`, `SavedRegs`, `IdtEntry`, `Idt`, `IdtPointer`, `Idt::load`, `Idt::with_default_handler` | `kernel/arch/x86_64/src/interrupts.rs` |
| Common ISR prologue (`tairix_arch_x86_64_isr_default`) | `kernel/arch/x86_64/src/interrupts.s` |

What lands:

- The CPU-pushed `InterruptStackFrame` (`rip`, `cs`, `rflags`,
  `rsp`, `ss`) is exposed as a `#[repr(C)]` struct with `offset_of!`
  pinned host tests against Intel SDM Vol 3A §6.14.2.
- The prologue's `SavedRegs` block (15 GPRs in push-descending
  order, `r15` at offset 0 through `rax` at offset `14*8`) is the
  Rust mirror of the assembly push sequence; layout is locked by a
  `const _: () = assert!(size_of == 15 * 8);` and by an `offset_of!`
  host test.
- `IdtEntry::interrupt_gate(handler, selector, ist)` builds a 64-bit
  interrupt gate (type `0x8E`, DPL 0) and the constructor masks `ist`
  to three bits so an attacker-controlled IST index cannot smear into
  `type_attr` (host tests `interrupt_gate_splits_handler_address` and
  `interrupt_gate_masks_ist_to_3_bits`).
- `Idt::with_default_handler(handler, selector, ist_for_exception)`
  populates all 256 slots in a single call; the caller-supplied
  closure picks an IST for each architectural exception
  (`percpu::init` uses it to wire vector 8 → IST 1, vector 2 → IST 2,
  every other slot → IST 0).
- The assembly prologue saves all 15 GPRs in the documented order,
  loads `rdi` with a pointer to the on-stack `SavedRegs`, aligns the
  stack to System V AMD64 §3.2.2, and calls
  `tairix_arch_x86_64_default_interrupt`. The Rust callee is
  `cfg(target_os = "none")` and `-> !`; it halts the binary via
  `qemu_exit::exit_failure` per AGENTS.md §10 (fail closed on every
  unexpected interrupt). Per-vector ISRs are deferred to the
  (c5) preemption commit, which will extend this surface via a
  `define_isr!` macro rather than expanding the default thunk.

### Stage 3a (c3) — context-switch primitive

| Piece | Source |
|---|---|
| `TaskCtx`, `TaskCtx::prepare`, `PrepareError`, `switch` (safe wrapper) | `kernel/arch/x86_64/src/context.rs` |
| `extern "C" fn tairix_arch_x86_64_switch(prev, next)` | `kernel/arch/x86_64/src/context.s` |

What the new `context` module provides:

- `TaskCtx { rsp: u64 }` — the per-task register-save area, layout
  pinned by `size_of` and `offset_of!` const-assertions so the
  assembly can address the `rsp` field via the constant offset
  `0x00(%rdi)` / `0x00(%rsi)`.
- `TaskCtx::prepare(stack_top, entry, arg)` synthesises the eight-
  qword resume frame the assembly's epilogue pops on first-run:
  `r15, r14, r13, r12, rbx, rbp = 0; rdi = arg; ret = entry`.
  The function rejects null / misaligned / too-small stacks
  (`PrepareError::{NullStack, Misaligned, TooSmall}`).
- The assembly side `tairix_arch_x86_64_switch` pushes the six
  callee-saved registers (`rbx, rbp, r12..r15`) plus `rdi` onto the
  outgoing task's kernel stack, records the resulting `rsp` into
  `(*prev).rsp`, loads `(*next).rsp`, pops the saved registers, and
  `ret`s. Pushing `rdi` unconditionally is what lets the same epilogue
  serve both a never-run task (whose synthesised frame holds the
  first-run argument in `rdi`) and a previously-suspended task.
- Caller-saved registers (`rax, rcx, rdx, rsi, r8..r11`) are deliberately
  *not* preserved: by System V AMD64 §3.2.1 they carry no live state
  across a `call` boundary. The `switch` symbol is reached only through
  a `call`, so no host-task code can observe a clobber.
- The bare-metal `switch` is gated behind `cfg(target_os = "none")`;
  host tests cover the `TaskCtx::prepare` frame layout in detail
  (`prepare_writes_initial_frame` reads back the eight qwords through
  a real, suitably-aligned stack arena).

### Stage 3a (c4) — scheduler preemption surface

`kernel/sched` gained a single new entry point in this slice:
`Scheduler::on_timer_tick(cpu)` (plus the observable counters
`Scheduler::preemption_count(cpu)` and
`Scheduler::total_preemption_count`). The arch port's timer ISR
calls `on_timer_tick` after acknowledging the device-level
interrupt source; the scheduler increments a per-CPU `AtomicU64`
counter (`Relaxed`-bumped) and returns. It does **not** itself call
`Scheduler::step` — the task registry `RwLock` and the overflow
`SpinLock` are explicitly forbidden from interrupt context by
`lib/sync`, so the cooperative `step` loop driven from kernel-
thread context remains the only writer of run-queue state. The
counter is the regression catcher; a future commit that lands
IRQ-safe locks can extend the entry point to drive a real
preemption step without changing the public signature.

The `SchedulerArch` trait is **not** extended in (c4). `send_ipi`
already documents the scheduler-asks-arch direction; the
arch-into-scheduler timer path is, by construction, a method on the
scheduler type and not on the arch trait (`AGENTS.md` §2.4 — no
interface creep, §15.5 — no parallel "convenience" method when the
existing one already covers the semantics).

The counter is the regression catcher Stage 2 lacked: a silent
revert to cooperative-only scheduling would keep the workload-
correctness invariants intact while breaking the security model
(`AGENTS.md` §5 — a runaway task on one CPU must not be able to
indefinitely block another). The `scheduler_stress_qemu`
integration test asserts `preemption_count(cpu) >= 10` per CPU at
the end of the workload; the threshold is intentionally well below
the >100 ticks per CPU a real run sees, so the assertion is
robust against QEMU TCG jitter without being a no-op.

### Stage 3a (c5) — LAPIC-timer-driven preemption

The arch crate's new `preempt` module wires the LAPIC timer into the
scheduler's `on_timer_tick` entry:

- **`define_isr!` macro** in `interrupts.rs` emits one `#[naked]`
  `extern "C" fn` per ISR. The body inlines the same 15-GPR push /
  16-byte stack align / call / 15-GPR pop / `iretq` sequence the
  default thunk in `interrupts.s` uses, but parameterised on the
  dispatcher symbol via `sym`. Vectors that push a hardware error
  code (`8`, `10`–`14`, `17`, `21`) are out of scope for the macro;
  they need a dedicated stub.
- **`preempt::TIMER_VECTOR = 0x20`** is the first user-installable
  IDT slot (Intel SDM Vol 3A §6.3.1) and the only consumer of the
  macro in this slice.
- **`preempt::tairix_arch_x86_64_timer_dispatch`** (the Rust
  trampoline the macro-emitted ISR stub calls) reads the LAPIC ID
  via a single MMIO read, maps it to the scheduler's dense `CpuId`
  through a 256-entry `LAPIC_TO_CPU_ID` table populated at bring-up
  time, invokes the installed callback, and writes `0` to the LAPIC
  EOI register. EOI is performed *after* the callback so a second
  tick cannot stack on the in-service bit; the callback runs with
  `IF = 0` (CPU clears it on interrupt-gate delivery), so the
  dispatcher itself is non-re-entrant by construction.
- **`preempt::init_local_preempt(cpu_index, &mut lapic, calibration)`**
  installs the timer ISR into the per-CPU IDT via the new
  `percpu::install_vector` (which writes a `volatile` `IdtEntry`
  through a raw-pointer cast — the CPU re-reads the IDT base on
  every delivery, so an entry overwrite while `IF = 0` is safe) and
  programs the LAPIC timer in periodic mode from the BSP-supplied
  `Calibration`.

Calibration on x86 derives from busy-waiting against the i8254 PIT
(`apic_timer::calibrate`), a single global device. Doing it
concurrently on every CPU would corrupt PIT channel 2. The
integration test therefore calibrates exactly once on the BSP and
APs re-use the result. This is correct on QEMU (one bus clock) and
on homogeneous single-package SMP Intel hardware; multi-socket
asymmetric hardware would need per-package re-calibration, which a
future commit can add behind the same `init_local_preempt` entry
point. The fail-loud cross-check is the per-CPU
`preemption_count >= 10` assertion in `scheduler_stress_qemu`.

What is *not* delivered yet (still tracked in `PLAN.md` Stage 3a
sub-checklist and in `.junie/next-session-prompt.md`):

- `kernel/core::KernelArch` impl wired into a new `tairix-kernel`
  binary (c7).
- Per-arch QEMU-runner module refactor in `tools/qemu` (d1).
- `PLAN.md` Stage 2 status block flip to `complete` (d2).

### Stage 3a (c6) — `syscall`/`sysret` entry

The `syscall_entry` module (`kernel/arch/x86_64::syscall_entry`)
owns the per-CPU machine state required to take a user-space
`syscall` instruction, marshal its register-passed arguments into
the architecture-neutral `tairix_kernel_syscall::RawArgs` layout,
and return to user space via `sysretq`. The architecture-neutral
dispatcher (validation, capability checks, audit) is owned by
`kernel/syscall` and is re-used verbatim — the arch port does not
duplicate the `SYSCALL_TABLE_HASH` validation surface
(AGENTS.md §2.2, §9).

The module is split along the same boundary as
`kernel/arch/x86_64::preempt`: pure host-testable MSR-value math
(`encode_star`, `efer_with_sce`, `fmask_value`, `pack_raw_args`),
per-CPU state (a fixed-size table of `SyscallTls` blocks, one per
CPU, each holding the kernel-stack top and a user-`%rsp` save
slot), and bare-metal pieces gated to `target_os = "none"` (the
naked `syscall_entry_stub`, its Rust trampoline
`tairix_arch_x86_64_syscall_dispatch`, and `init_local_syscalls`).
A `SyscallDispatchFn` callback (`set_dispatch_callback`) is the
single integration point with the binary's
`tairix_kernel_syscall::Dispatcher` — the (c7) binary commit is the
only writer of that callback.

`init_local_syscalls` programs five MSRs on the calling CPU
(Intel SDM Vol 3A §5.8.8, §2.7):

| MSR | Address | Purpose |
| --- | --- | --- |
| `IA32_EFER` | `0xC000_0080` | Set `SCE` (bit 0) to enable `syscall`/`sysret`. |
| `IA32_STAR` | `0xC000_0081` | Encode the kernel CS/SS pair (entry) and the user CS/SS triplet (sysret). |
| `IA32_LSTAR` | `0xC000_0082` | Linear address of `syscall_entry_stub`. |
| `IA32_FMASK` | `0xC000_0084` | Clear `IF`/`TF`/`DF`/`AC`/`NT`/`RF`/`VM`/`IOPL` on entry (value `0x7_7700`). |
| `IA32_KERNEL_GS_BASE` | `0xC000_0102` | Per-CPU `SyscallTls` address (swapped in by `swapgs`). |

The naked `syscall_entry_stub`:

1. `swapgs` — `%gs` now points at this CPU's `SyscallTls`.
2. Save the user `%rsp` into `gs:8` and load the kernel `%rsp`
   from `gs:0`.
3. Push the user `RFLAGS` (`%r11`) and saved RIP (`%rcx`) plus a
   padding slot so the System V "rsp ≡ 0 (mod 16) at `call`" rule
   holds.
4. Build the `SYSCALL_MAX_ARGS`-wide argument array on the kernel
   stack from `rdi`/`rsi`/`rdx`/`r10`/`r8`/`r9`.
5. Call `tairix_arch_x86_64_syscall_dispatch` with `%rdi = syscall
   number` (the saved `%rax`) and `%rsi = &args[0]`.
6. Pop the argument array back into `rdi`/`rsi`/`rdx`/`r10`/`r8`/`r9`
   — restoring the caller's argument registers, never a bare stack
   drop: the user-side trap stub (`lib/abi-trap`) declares only
   `rax`/`rcx`/`r11` clobbered across `syscall`, so returning dispatch
   residue in those registers would miscompile callers *and* leak
   kernel register contents to ring 3 (pinned by the
   `tairix-test-syscall-regs-qemu-x86_64` vertical) — then pop the
   saved `%r11`/`%rcx`, restore the user `%rsp`, `swapgs`, `sysretq`.

The fail-closed posture is the same as the default ISR
(`interrupts::tairix_arch_x86_64_default_interrupt`): if a syscall
reaches the trampoline before the binary installed its dispatch
callback, the kernel exits the QEMU run with failure via
`qemu_exit::exit_failure` rather than returning an unspecified
value to user space (AGENTS.md §7).

`unsafe`-block accounting introduced by (c6) (all encapsulated
behind safe APIs and covered by host unit tests for the invariants
that are not the privileged instruction itself):

| Site | Justification |
| --- | --- |
| `install_kernel_rsp0` raw-pointer writes | Caller pins `cpu_index` to this CPU; no other CPU touches the slot. The stack top is first validated (canonical, kernel-half, 16-byte aligned, non-null) by `validate_kernel_rsp0`, rejecting a stack-pivot / user-range `RSP0` (`tests/SECURITY.md` §3.5 / §5, CVE-2019-1125). |
| `rdmsr` / `wrmsr` `asm!` blocks | CPL=0 + caller-validated MSR address + host-tested MSR value. |
| `init_local_syscalls` `wrmsr` sequence | Forwarded contract; each value is constructed by the host-tested encoders. |
| `dispatch_callback` / trampoline `transmute` | Every store into the callback slot round-trips a valid `SyscallDispatchFn` (mirrors `preempt::set_timer_callback`). |
| Naked `syscall_entry_stub` | Reachable only via the CPU's `syscall` instruction; the rustdoc spells out the entry/exit invariants. |

The five MSR encoders + the `SyscallTls` layout + the per-register
argument packing are covered by host unit tests in
`syscall_entry::tests` (including the `tests/SECURITY.md` §5
adversarial-`RFLAGS` check that `IA32_FMASK` masks off `AC`/`DF`/
`IOPL` on entry, and the §3.5 / §5 `validate_kernel_rsp0` checks that a
non-canonical, user-range, misaligned, or null kernel `RSP0` is rejected
fail-closed before `install_kernel_rsp0` can store it — the stack-pivot /
CVE-2019-1125 class); the bare-metal `wrmsr` and naked-entry
paths are exercised end-to-end by the (c7) binary commit's QEMU
integration test.

Each of these items is *individually* a multi-step kernel change
needing tests + rustdoc + docs updates in the same commit; landing
them in a single session would have forced shortcuts AGENTS.md §15
forbids. The continuation prompt enumerates them verbatim so the
next session can pick them up.

Four `// SAFETY:`-annotated `unsafe` regions are introduced by this
stage, all encapsulated behind safe APIs: the `core::arch::global_asm!`
that embeds the trampoline payload, the `read_volatile` of the LAPIC ID
register (`smp::bsp_lapic_id`), the byte-exact `copy_nonoverlapping`
from the assembled payload to physical `0x8000`
(`smp::TrampolineFrame::install`), and the `Acquire`-load of the
`ready` flag through an `AtomicU32` raw-pointer cast against the
in-frame bytes (`smp::TrampolineFrame::load_ready`).

### Prerequisites

The Stage-2 QEMU pipeline expects a Linux host with:

- The pinned TAIRiX nightly toolchain (see `rust-toolchain.toml`) plus the
  `x86_64-unknown-none` cross target.
- `qemu-system-x86_64` ≥ 8.0. Nothing else: the kernels are PVH
  direct-booted via `-kernel`, so no bootloader, boot-media tool, or
  firmware package is involved.

If any of these are missing, `cargo xtask test --qemu` exits with a clear
diagnostic naming the missing package (`AGENTS.md` §15.10 — no silent
skips, no flaky bypasses).

### Invocation

```text
cargo xtask test --qemu
```

This is the *only* sanctioned entry point. It:

1. Runs the standard `cargo test --workspace --all-targets --locked`
   pass first (host-side tests including the workspace-level
   `tests/integration/scheduler_stress`).
2. Builds each enrolled QEMU test for `x86_64-unknown-none`.
3. PVH direct-boots each kernel ELF under QEMU via `-kernel`, with
   `-display none -serial stdio` and the `isa-debug-exit` device on
   port `0xf4`.
4. Enforces the per-test strict *inactivity* timeout: a guest is killed
   only once it produces no new serial output for its whole budget, so a
   guest that is merely slow (co-scheduled, or on a slow host core) is never
   killed while it keeps making progress. **No retries.** A genuine
   no-progress timeout is a hard failure (`AGENTS.md` §7).

A passing run looks like:

```text
xtask: [test --qemu] 1 test(s) enrolled
xtask: [test --qemu (build tairix-test-memory-isolation)] cargo build ...
xtask: [test --qemu (run tairix-test-memory-isolation)] kernel=... cpus=1 timeout=60s
```

Failure modes are reported through `tairix_qemu::Outcome`:

- `Pass` — kernel wrote `0x10` to `0xf4`; `xtask test --qemu` exits 0.
- `Fail` — any other QEMU exit status; the captured serial transcript is
  printed verbatim.
- `Timeout` — the guest fell silent for its whole inactivity budget;
  `cargo xtask` errors out with that budget and the partial serial
  transcript.

## Stage 4.D — virtio-blk backing storage in the QEMU runner

The Stage 4.D `PciTransport` (`drivers/bus/virtio`) drives a real
modern virtio-1.x PCI function, and the boot-time PCI walk
(`tairix_kernel::provision_virtio_pci`) discovers it. To exercise that
path end to end, a QEMU integration test must (a) present the guest with
a `virtio-blk-pci` function and (b) know the device's contents before
boot so the kernel side can assert on a planted sector. The runner now
owns both halves:

- **Disk planting** — `tools/qemu/src/disk.rs::plant_raw_disk(path,
  size_sectors, sectors)` writes a zero-filled raw image and stamps each
  `(lba, bytes)` entry at offset `lba * SECTOR_BYTES`. The raw format is
  deliberate: the on-disk offset of a block is exactly `lba *
  SECTOR_BYTES`, so the host harness can re-read the image after the run
  to verify a guest write without a qcow2 parser. Validation fails
  closed (`InvalidInput`) on a zero-sector image, an out-of-range `lba`,
  or a slice longer than `SECTOR_BYTES`, and no file is created in those
  cases.
- **Device attachment** — `Spec::with_virtio_blk(image)` records a
  `BlockDevice`, and the x86_64 backend emits, per device, `-drive
  if=none,format=raw,id=blkN,file=<image>` paired with `-device
  virtio-blk-pci,drive=blkN`. `if=none` keeps the drive off any
  automatic controller so the explicit virtio function is the only thing
  the guest sees — that is the function the boot walk discovers.
  `Runner::run` checks every backing image exists before spawning QEMU,
  so a missing image is a clean `NotFound` rather than an opaque
  mid-boot QEMU abort.

The argv emission, the no-storage case, and the validation paths are
covered by host unit tests in `tools/qemu/src/x86_64.rs::tests` and
`tools/qemu/src/disk.rs::tests`. The
kernel-side test crate that consumes this surface
(`tests/integration/virtio_blk_pci_x86_64`) has landed and is enrolled in
`cargo xtask test --qemu` (see *Stage 4.D — virtio QEMU verticals* below).

## Stage 4.D / NETWORK N3c — virtio-net dgram networking in the QEMU runner

The netstack vertical (`tests/integration/netstack_*`) needs a network
interface the kernel can drive end to end, a link peer to converse
with, and a way for the host to observe the on-wire exchange. The
runner supplies all three, in the same shape as the virtio-blk
attachment above:

- **Device attachment** — `Spec::with_virtio_net_dgram(qemu_sock,
  peer_sock, pcap)` records a `NetDevice`, and the x86_64 backend
  emits, per device, `-netdev dgram,id=netN,local.type=unix,
  local.path=<qemu_sock>,remote.type=unix,remote.path=<peer_sock>`
  paired with `-device virtio-net-pci,netdev=netN,disable-legacy=on`.
  `disable-legacy=on` pins the function to the modern virtio-1.x PCI
  layout the boot walk decodes (device id `0x1041` = `0x1040 +
  virtio-net`), exactly as for virtio-blk. The aarch64/riscv64 backends
  emit the `virt`-board analogue, `-device virtio-net-device,netdev=netN`.
- **Datagram backend + harness peer** — the `dgram` netdev carries one
  raw Ethernet frame per unix datagram: QEMU binds `qemu_sock` and
  sends every guest frame to `peer_sock`, which the harness binds
  *before* the run. The harness-side peer
  (`tools/xtask/src/commands/netpeer.rs`) is the same pure `lib/net`
  `Stack` the guest's netstack drives, configured from the shared
  `tairix-test-netstack-wire` topology (guest `192.0.2.15`, peer
  `192.0.2.2`, link-local `fe80::15`/`fe80::2`), so the exchange is
  deterministic, private per run, and needs no host privileges
  (`AGENTS.md` §7 — no flaky tests, no port collisions).
- **On-wire capture** — when a `NetDevice` carries a `pcap` path the
  backend attaches `-object filter-dump,id=dumpN,netdev=netN,file=<path>`,
  which mirrors every frame on the interface to a host `pcap` file. The
  host harness (and a developer chasing a failure) can read the whole
  neighbour + echo exchange from that file after the run, the same way
  `plant_raw_disk` lets it verify a guest disk write — no
  packet-capture library is linked into the guest.

The argv emission (per-device attachment, the no-network case, the
capture-free vs. captured cases, and the PCI-BAR confinement for a
net-only spec) is covered by host unit tests in
`tools/qemu/src/x86_64.rs::tests` and `tools/qemu/src/riscv64.rs::tests`.
The kernel-side network verticals — the **two-process** production-boot
`tests/integration/netstack_autoload_qemu_{x86_64,aarch64,riscv64}` — are
enrolled in `cargo xtask test --qemu` (see below).

## Stage 4.D — virtio QEMU verticals (shared bring-up)

The x86_64 virtio QEMU integration tests boot the production
`tairix-kernel` pipeline and, on `AuditEvent::BootCompleted`
(`EventId(4004)`), drive a real (emulated) modern virtio-1.x PCI device
end to end. The device-agnostic bring-up is identical for every device
class, so it lives once in the shared `tairix-test-virtio-qemu-support`
crate (`tests/integration/virtio_qemu_support`; `AGENTS.md` §2.2) rather
than being copied per vertical:

- `run_virtio_scenario(cfg, body)` carves a high, identity-mapped
  per-device DMA region from the published firmware memory map, walks
  PCI through `mechanism_one(x86_port_io())` — the bus driver's
  architecture-neutral mechanism-#1 constructor fed the x86_64
  `tairix_abi::PortIo` backend from `tairix_arch_x86_64::pio`
  (`AGENTS.md` §17.2 / §17.4) — maps the four virtio register windows
  through the `CAP_MMIO_MAP`-gated `KernelMmioMapper`, builds a
  `PciTransport`, binds a (masked) IO-APIC GSI and routes the device's
  MSI-X interrupt, mints a `KernelVirtioHost` over the carved pool, then
  enables MSI-X and hands the provisioned transport + host to a
  device-specific closure.
- The signed `.rxe` is driven through the full `tairix_drvhost::Host`
  lifecycle — `load → snapshot → reload → unload` — against the live
  `KernelVirtioFactory`. The device-specific closure runs *after* the
  reload and *before* the unload, so every vertical proves a reloaded
  driver still brings its real device online and round-trips I/O. This
  is the Stage 4.D Item 4 **unload → reload → reuse** deliverable,
  implemented once in the shared bring-up (`AGENTS.md` §2.2) rather than
  as a separate per-driver test. Every lifecycle transition that
  misbehaves flips QEMU failure with a serial breadcrumb (`AGENTS.md`
  §7 — no weakened tests).
- `define_boot_harness!(scenario)` generates the boot-observer `Sink`,
  the `#[panic_handler]` bridge, and the `kernel_main` entry point; the
  crate also owns the shared bump `#[global_allocator]`. Every item is
  gated to `x86_64-unknown-none`, so a host `cargo build --workspace`
  compiles the crate to an empty library.

`tests/integration/virtio_blk_pci_x86_64` builds on it: it reads sector 0
(verifying the planted `byte[i] = i mod 256` pattern), then writes a
distinct pattern to sector 1 and reads it back. It is enrolled in
`tools/xtask/src/commands/qemu_tests.rs` (single CPU, 60-second budget,
no retries per `AGENTS.md` §7).

The network path is no longer a single-process engine vertical on this
shared bring-up: it is exercised by the **two-process** production-boot
`tests/integration/netstack_autoload_qemu_x86_64` (`plans/NETWORK.md`

`tairix-netstack` service in another. That entry sets a
`netstack_peer` mode so the runner attaches the dgram interface, the
harness-side peer thread, and a frame-dump capture.

## Stage 3a (c7-arch) — `SchedulerArch` impl for x86_64

Stage 3a (c7) is split into two commits: **(c7-arch)** lands the
architecture trait impl alongside the existing primitives, and
**(c7-bin)** lands the freestanding `tairix-kernel` binary that
composes it with `kernel/core`. (c7-arch) is in this commit.

### Surface

| Item | Module |
|---|---|
| `X86_64Arch` (`SchedulerArch` impl, `ArchInitError`, `lapic_id_of`, `boot_cpu_id`, `boot_cpu_lapic_id`) | `kernel/arch/x86_64::kernel_arch` |
| `halt() -> !` free function | `kernel/arch/x86_64::kernel_arch` |
| `RawArgs` layout assert (compile-time) | `kernel/syscall::table` |

`X86_64Arch` implements the Arch HAL trait
`tairix_arch_api::SchedulerArch` (`AGENTS.md` §17.2). The HAL crate
`kernel/arch/api` is the §17.4 boundary: a port names it (and `lib/*`)
instead of a concrete kernel crate, so `tairix-arch-x86_64` no longer
depends on a scheduler crate. `kernel/sched/api` re-exports the trait, so
the single impl still satisfies every `tairix_kernel_sched_api::SchedulerArch`
bound in the scheduler.

The module is feature-gated behind the optional Cargo feature
`sched-arch` on `tairix-arch-x86_64`. The feature pulls the
`no_std`, dependency-free `tairix-arch-api` into the dependency graph
and compiles the `kernel_arch` module. It stays optional so a
freestanding consumer that does not need the arch handle (e.g.
`tests/integration/memory_isolation`, which exercises page-table
isolation rather than scheduling) compiles neither — `AGENTS.md`
§2.3, pay only for what you use. The arch crate's dev-dependencies
enable `sched-arch` through a self-link so `cargo test` always
exercises the module — mirrors the `test-arch` convention used by
`kernel/sched` and `kernel/core`.

### Semantics

- **`current_cpu`** — on bare metal, reads the LAPIC ID register
  (`LAPIC_BASE_PHYS + 0x20`) volatilely and consults the
  `preempt::LAPIC_TO_CPU_ID` mapping table via
  `preempt::cpu_id_for_lapic`. If the table has not yet been
  populated (only possible during the very first instructions after
  the trampoline hand-off, before AP bring-up calls
  `preempt::set_cpu_id_for_lapic`), it falls back to the boot CPU's
  dense `CpuId` — a fail-closed choice that never invents an
  out-of-range `CpuId` (`AGENTS.md` §5.4.5). On host, it returns
  the boot CPU's dense `CpuId` directly so scheduler host tests
  remain deterministic (`AGENTS.md` §7 — no flaky tests).
- **`ticks_now`** — on bare metal, executes `RDTSC` via inline
  assembly (no MMIO, no memory clobber). The invariant TSC modern
  x86_64 CPUs expose is monotonically non-decreasing on a single
  CPU, which is what the `SchedulerArch` contract requires. That
  invariance is not assumed blindly: the boot path validates the
  CPUID Invariant-TSC flag through `tsc::detect_invariant_tsc` and
  fails closed before any multi-CPU use (boot pipeline step 6b below;
  rationale in `docs/src/security/side_channels.md`). On
  host, returns a per-instance `AtomicU64::fetch_add(1, Relaxed) +
  1`, keeping monotonicity in the host test path without sharing
  global state across parallel `cargo test` workers.
- **`send_ipi`** — on bare metal, constructs an ephemeral
  `apic::Lapic<VolatileLapicMmio>` over `LAPIC_BASE_PHYS` and sends
  a fixed-mode IPI on `preempt::TIMER_VECTOR` to the target's APIC
  ID, resolved through the `cpu_to_lapic` map the handle borrows
  from its caller-provided `X86_64ArchStorage` (`AGENTS.md` §24.1). Out-of-
  range / unmapped targets are dropped (and counted in the host-
  only stray counter on host builds) — the architecture-neutral
  contract documents `send_ipi` as best-effort. Each CPU's
  `send_ipi` access goes through that CPU's own LAPIC at the same
  physical address, so two CPUs calling concurrently do not race;
  within a single CPU the call is non-re-entrant by convention.
- **`halt`** (free function) — `cli` then `loop { hlt }`, both
  emitted via `core::arch::asm!` with the documented `nomem,
  nostack, preserves_flags` option set. The function's `-> !`
  return type is the contract; a compile-time `const _: fn() -> !`
  assertion in the test module proves the signature without
  blocking the test runner.

### `RawArgs` layout assertion

## Stage 3a (c7-bin) — `tairix-kernel` binary

The second half of Stage 3a (c7) lands the freestanding
`tairix-kernel` binary, a hybrid `[lib]` + `[[bin]]` crate at
`kernel/tairix-kernel/`. The library half ships the boot pipeline
re-used by both the production binary and the new QEMU integration
test (`tests/integration/kernel_arch_boot`); the binary half adds
the production `#[global_allocator]`, the `#[panic_handler]`, and
the `extern "C" fn kernel_main` symbol the arch trampoline calls.

### Pipeline

`tairix_kernel::boot(boot_info, log_sink, audit_sink) -> !`
performs, in order (steps 1–10a below plus the IO-APIC discovery are the
shared, composable board bring-up `x86_64::boot::bring_up_bsp`, which owns
every set-once install and returns the discovered board facts —
`BspBringUp { bsp_lapic_id, cpu_to_lapic, calibration, memory_map,
irq_routing }`; the private `try_boot` composes it with the arch-handle
construction and the `BootInfo` assembly of step 11. A QEMU chassis that
needs the production dispatch/user-fault path without `kernel_main` — the
SP11e stack-grow vertical — runs the same `bring_up_bsp` and installs its
own production-typed hook into the `DISPATCH_SLOT` the installed callbacks
resolve through, so the bring-up ordering is never forked):

1. `percpu::init(0)` — BSP per-CPU GDT/IDT/IST.
1b. `percpu::install_vector(0, 14, fault::page_fault_isr_addr())` —
    overwrite the `#PF` (vector 14) slot, which `percpu::init` left on the
    no-error default thunk, with the dedicated, error-code-aware page-fault
    entry (`tairix_arch_x86_64::fault`). The entry decodes the hardware
    error code, captures `CR2`, and routes to the set-once `fault` observer,
    or — with none installed — preserves the exact fail-closed default
    (`AGENTS.md` §2.9 / §2.17). This is the x86_64 analogue of the
    riscv64/aarch64 `fault` hooks. The boot pairs it with
    `tairix_arch_x86_64::uaccess::install()` — arming the guarded
    user-copy fault window (`tairix_arch_api::uaccess`), whose in-window
    kernel-mode `#PF` the entry redirects to the copy's fix-up so a
    violated uaccess proof surfaces as an error, never a halt; a
    conflicting slot refuses the boot (fail closed).
2. Software-enable the BSP LAPIC; read its ID via `smp::bsp_lapic_id`.
3. `apic_timer::calibrate` against the PIT (10 ms window, 1 ms
   period).
4. Boot-info parse (`bootinfo::BootData::load` — multiboot2 or PVH,
   per the protocol the entry stub recorded) → `BootMemoryMap` via
   `bootmemory::iter_from_*`.
5. RSDP → `acpi::locate_madt` → `acpi::Madt::parse`; verify the
   BSP's LAPIC is enumerated (ACPI Processor-Enabled bit 0 set).
6. Build the `cpu_to_lapic` map with slot 0 populated from MADT
   (single-CPU bring-up; returned in `BspBringUp` so every caller's
   arch handle is built from the one definition).
6a. `tsc::detect_invariant_tsc` — read the CPUID Invariant-TSC flag,
    log the decision (`KERNEL_BOOT_TSC_INVARIANCE`), and fail closed
    (`BootError::TscNotInvariant`) if more than one CPU is active on a
    part that does not advertise it. A single-CPU boot proceeds
    regardless — one TSC is self-monotonic — so the QEMU default CPU
    (no `invtsc`) still boots (`AGENTS.md` §19.1).
    (`X86_64Arch::new(&ARCH_STORAGE, 0, bsp_lapic_id, &cpu_to_lapic)`
    itself runs in `try_boot`, after the bring-up returns: the handle
    borrows its per-CPU bookkeeping from a caller-owned
    `static X86_64ArchStorage<1>` — production `tairix-kernel` runs
    single-CPU — so no fixed `MAX_CPUS` ceiling is baked into the arch
    crate, `AGENTS.md` §24.1, and a chassis builds its own handles from
    the same returned facts.)
7. `syscall_entry::set_dispatch_callback(production_dispatch)` —
   **before** any CPU enables `syscall` (the trampoline contract) —
   paired with `fault::set_user_fault_resolver(production_user_fault)`,
   so the demand-paged file and stack-growth `#PF` resolution is in
   place before user space exists; a second resolver occupant refuses
   the boot (`BootError::UserFaultResolverInstall`, fail closed).
8. `preempt::init_local_preempt(0, &mut lapic, calibration)` —
   install the timer ISR + arm the LAPIC timer.
9. `preempt::set_cpu_id_for_lapic(bsp_lapic_id, 0)`.
10. `syscall_entry::init_local_syscalls(0, kernel_cs, sysret_user_base,
    kernel_rsp0)` — enable `syscall`/`sysret` on the BSP, with
    `kernel_rsp0` provided by the binary's per-CPU stack pool.
10a. `percpu::install_tss_rsp0(0, kernel_rsp0)` — program the TSS `RSP0`.
    `init_local_syscalls` set the *syscall* entry stack (loaded via
    `swapgs`), but a ring-3 CPU exception (`#PF`/`#GP`) or a hardware IRQ
    that preempts a user task is delivered through the IDT, for which the
    CPU loads `TSS.RSP0`. Left zero (the `percpu::init` default), the
    interrupt-frame push faults and escalates to `#DF`, so a user trap is
    *undeliverable* — a security gap, not a feature (`AGENTS.md` §2.9 /
    §2.17). The trap stack is the same already-mapped per-CPU kernel stack
    the syscall path uses (Linux likewise shares one kernel stack for
    syscalls and traps); `RSP0` is only loaded on a ring-3 → ring-0
    transition, when that stack is idle, so there is no overlap with an
    in-flight syscall. The value is checked by the **one** shared
    stack-pivot validator `syscall_entry::validate_kernel_rsp0` (§2.2), so
    a non-canonical / user-range / misaligned / null `RSP0` fails closed.
11. Build `BootInfo<'static, BinArch>` and forward to
    `tairix_kernel_core::kernel_main`.

Step 7 is the *order* the prompt mandates: the trampoline fail-closes
via `qemu_exit::exit_failure` if it fires before a callback is
installed (see `kernel/arch/x86_64::syscall_entry`'s
`SYSCALL_DISPATCH_CALLBACK` rustdoc and `AGENTS.md` §5.4.5).

### Production dispatch callback

The callback installed in step 7 is `production_dispatch`
(Stage 2.7 follow-up (f5)). It satisfies the trampoline's ordering
contract — the callback is installed before `init_local_syscalls`
enables `syscall` — and then forwards every syscall through the
per-binary `DISPATCH_SLOT`, which `kernel_core::kernel_main`
publishes during the `Phase::Syscall` init step
([Syscall registration phase](../architecture/kernel.md#syscall-registration-phase)).

`production_dispatch` is `extern "C" fn(u64,
*const [u64; SYSCALL_MAX_ARGS]) -> u64` and its ABI is locked at
compile time by `_DISPATCH_SIGNATURE_PINNED` in
`kernel/tairix-kernel/src/x86_64/dispatch.rs`. The body:

1. Reads the kernel-stack frame into a `RawArgs` value via the
   `read_raw_args` helper.
2. Calls `DISPATCH_SLOT.get()` and forwards the call through the
   resident `DispatchHook`.
3. Encodes the `DispatchOutcome::Returned(SyscallResult)` back into
   `%rax`: `Ok(v) → v`; `Err(e) → (-(e.as_i32() as i64)) as u64`
   (Linux-style negation).
4. Halts the CPU forever via `kernel_arch::halt` on `DispatchOutcome
   ::NoCallerContext` (the hook already emitted
   `AuditEvent::SyscallNoCallerContext` by then) or on an empty slot
   (a syscall fired before `kernel_main` published the hook — only
   reachable if BSP ordering is wrong; `AGENTS.md` §5.4.5 — fail
   closed).

### MADT-finder consolidation

The bin's boot pipeline and the existing

### Kernel heap allocator

`src/kalloc.rs` re-exports the shared `tairix_kalloc::FreeListAllocator`
(`lib/kalloc`), registered over a static page-aligned `Heap` as the
binary's `#[global_allocator]`. It is a thread-safe (spin-lock-guarded)
coalescing first-fit free-list allocator: `dealloc` returns blocks to
the list and merges adjacent free blocks, so steady allocate/free
traffic runs in bounded memory. Exhaustion returns `null_mut` per the
`GlobalAlloc` contract — allocation failure is a fallible signal, never
a panic (`AGENTS.md` §4). The crate's `README.md` documents the
bounds-checking invariants.

### Per-CPU kernel stacks

`src/boot.rs` declares a `static mut KERNEL_STACKS: [KernelStack;
MAX_CPUS]` of 64 KiB, 16-byte-aligned stacks (matching the BSP
bootstrap stack in `kernel/arch/x86_64/src/boot.s`). Only slot 0 (the
BSP) is consumed at this stage; the remaining slots are reserved for
Stage 2.7 AP bring-up. Access goes exclusively through
`kernel_stack_top(cpu_index)` which range-checks the index. The size
was raised from 16 KiB to 64 KiB because the Stage-5 QEMU storage
verticals drive a full filesystem `open` (which stages whole blocks
through on-stack scratch buffers) synchronously on the boot thread,
nested inside the audit observer's `BootCompleted` callback; 16 KiB
was marginal there and an overflow silently corrupted the adjacent
bootstrap page tables.

### `.cargo/config.toml` change

`x86_64-unknown-none` gains `--cfg curve25519_dalek_backend="serial"`:
the `lib/crypto` → `ed25519-dalek` → `curve25519-dalek` chain
auto-selects the `simd` backend on nightly toolchains advertising

`x86_64-unknown-none`. The `serial` backend is what upstream ships

### Stage 2.7 follow-up (f6) — `tairix-test-syscall-dispatch-qemu`

The integration test bin under
`tests/integration/syscall_dispatch_qemu` is the QEMU half of
PLAN.md's "Stage 2.7 follow-up — Production syscall wiring" thread.
It boots the production `tairix-kernel` pipeline (boot info →
ACPI/MADT → BSP `X86_64Arch` → per-CPU init → `BootInfo` →
`kernel_core::kernel_main`) and replaces only the audit Sink. The
replacement sink, on observing `AuditEvent::BootCompleted`,
synthesises a fresh `Scheduler<BinArch>` / `RwLock<CapTable>` /
`KernelSyscallHandlers<'_, BinArch>` / `Dispatcher` quartet on the
stack, registers one task plus its capability record carrying
`CAP_TIME_SET`, and drives two `Dispatcher::dispatch` calls:

1. `(cap_query, CAP_TIME_SET)` — must return `Ok(1)`. `cap_query`
   is `audit: false` in the `abi-v1` table, so capability probes
   do not flood the audit log; observability for this leg comes
   from the dispatcher's `SyscallResult` return value. The
   synthesised inner audit sink must still see zero
   `SyscallInvoked` records at this point.
2. `(exit, 0)` — must succeed. `exit` is `audit: true`, so the
   dispatcher emits exactly one `AuditEvent::SyscallInvoked`
   (`EventId(5000)`) record through the inner sink, which the
   test bin counts. Any other count — zero (missed record) or two
   (spurious duplicate) — flips `qemu_exit::exit_failure`.

The bin's `test-hooks` Cargo feature is on by default; release
builds that enable it are rejected by a `compile_error!` guard,
and `deny.toml`'s `[[bans.features]]` rule forbids the production
`tairix-kernel` crate from ever growing the same feature
(AGENTS.md §1, §5.4.5, §15).

### CCOMPAT CC2 — `tairix-test-abi-sys-syscall-qemu`

The integration test bin under
`tests/integration/abi_sys_syscall_qemu` is the `plans/CCOMPAT.md`
stage CC2 per-native-target round-trip for the C-callable syscall
stub runtime (`lib/abi-sys`). Where `tairix-test-syscall-dispatch-qemu`
drives `Dispatcher::dispatch` directly and never executes a trap
instruction, this bin actually *issues* the trap, so the `syscall`
instruction (`lib/abi-sys/src/trap.rs`) and the kernel's `IA32_LSTAR`
entry stub (`kernel/arch/x86_64/src/syscall_entry.rs`) are exercised
together.

It boots the same production pipeline and, on
`AuditEvent::BootCompleted`, **overrides** the syscall dispatch
callback (the production callback fail-closes without a user caller
context, which this test does not have) and then calls the `abi-sys`
stub `tairix_sys_cap_query` with `CAP_TIME_SET`. Issuing `syscall` from
ring 0 enters the kernel entry stub exactly as a ring-3 call does
(`swapgs`, switch to the per-CPU kernel stack, rebuild the canonical
`[u64; SYSCALL_MAX_ARGS]` array), so the installed callback observes
the register marshalling end-to-end. It asserts the dispatched number
is `SyscallNumber::CAP_QUERY` and argument 0 is the capability id (the
rest zero), then flips `qemu_exit::exit_success`; any mismatch — or the
`syscall` returning to its caller at all — flips
`qemu_exit::exit_failure`. The `syscall` masks `RFLAGS.IF` via
`IA32_FMASK`, so the callback runs with interrupts disabled. The
callback never returns: the entry stub's `sysretq` would drop the CPU
to ring 3 with no user context, so the test exits QEMU from inside the
callback instead.

The aarch64/riscv64 CC2 round-trips need an `EL0`/`U-mode` user context
to raise `svc`/`ecall` from (a kernel-mode `svc`/`ecall` is not the
user-syscall path). Rather than wait for the program loader, those
tests stand up a minimal lower-privilege context themselves with the
Stage-3 paging primitives and have now landed —
`tairix-test-abi-sys-syscall-qemu-riscv64` (`sret` to U-mode) and
`tairix-test-abi-sys-syscall-qemu-aarch64` (`eret` to EL0); see their
platform pages and `plans/CCOMPAT.md`.

The bin's `test-hooks` Cargo feature mirrors
`tairix-test-syscall-dispatch-qemu`: on by default, rejected in release
builds by a `compile_error!` guard (AGENTS.md §1, §5.4.5, §15).

## Platform discovery (hardware tree)

The x86_64 port implements the Arch HAL `PlatformDiscovery` slice
(`AGENTS.md` §17.2 / §18.2) in `kernel/arch/x86_64::platform`. The
`AcpiDiscovery` reader takes the bytes of an already-located ACPI MADT
(`acpi::Madt::parse`) and normalises it into the single `lib/abi`
hardware tree (`hwtree`): a root node, one `Cpu` node per *enabled*
Local APIC entry, and one `InterruptController` node per I/O APIC,
carrying the controller's MMIO register window as a capability-gated
(`CAP_MMIO_MAP`) `HwResource` — never an ambient handle (§4). This is a
tracked move of the Local-APIC enumeration the SMP bring-up already
performs behind the common HAL trait (§2.2), not a second parser. The
reader is pure byte-slice input, so it is host-tested without a
bare-metal target and exercised by the port's
`passes_arch_hal_conformance_suite`.

## Per-CPU storage (GS base)

The x86_64 port implements the Arch HAL `PerCpu` slice (`AGENTS.md`
§17.2) in `kernel/arch/x86_64::percpu_hal` over the **GS base** — the
`IA32_GS_BASE` MSR (`0xC000_0101`). While in the kernel the active GS
base is the per-CPU anchor (the syscall stub's `swapgs` makes the
kernel's per-CPU TLS the active base on entry), so
`PerCpuStorage::read_self_base` / `write_self_base` are an `rdmsr` /
`wrmsr` of that MSR. This is distinct from the `percpu` module, which
owns the per-CPU GDT/IDT/IST-stack bring-up the GS base points *at*; this
slice is the generic read/write of the base register itself. The stored
word is opaque (the kernel decides whether it holds a per-CPU
control-block address or a dense `CpuId`). On the host build there is no
GS base, so the handle backs the word with an in-handle cell solely for
the round-trip + isolation conformance verticals (`percpu::conformance`),
folded into the port's `passes_arch_hal_conformance_suite`. The module is
gated on the `sched-arch` feature, like the other Arch HAL slices.

## Interrupt controller (IO-APIC)

The x86_64 port exposes the Arch HAL `IrqController` slice (`AGENTS.md`
§17.2 / `plans/WIRING.md` Stage W3). Because the multi-IO-APIC controller
needs `alloc` (one block per IO-APIC), it lives in the downstream
`kernel/tairix-kernel::ioapic_controller::IoApicController` rather than in
the `no_std` arch crate (the arch crate carries the host-testable
single-IO-APIC `IoApic` driver behind the `IoApicMmio` seam). The HAL
`IrqController` impl there forwards `mask` to the controller's existing
consumer-side `kernel/irq::IrqController::mask` (the cached-redirection-
entry rewrite + `SeqCst` fence) and `unmask` to the inherent `unmask`,
mapping the "no such addressable line" error to
`IrqControlError::OutOfRange`. The consumer-side
`kernel/irq::IrqController::rearm` is overridden to unmask the line (over
the inherent `unmask`): `IrqTable::fire` masks a line before its waiter
observes the wake (mask-before-wake), so a user-space interrupt-driven
driver's `irq_wait` park path re-enables its INTx line through `rearm` on
the driver's behalf — the sibling of the aarch64 GIC / riscv64 PLIC re-arm
(the default no-op would leave the line masked-forever after the first
completion). x86_64 is **vectored** — the IDT vector
identifies the source and end-of-interrupt is a single LAPIC write that
names no line — so it deliberately implements no `InterruptEntry`; there
is no claim register to model (`AGENTS.md` §2.1). The
`ioapic_controller_passes_arch_hal_irq_conformance` host test drives
`irq::conformance::run_controller` over a real controller on a
`RecordingMmio` mock (a programmed GSI valid, an out-of-range GSI
rejected).

## Timer programming (`Timer`)

The x86_64 port implements the Arch HAL `Timer` slice (`AGENTS.md`
§17.2 / `plans/WIRING.md` Stage W4) in `kernel/arch/x86_64::timer_hal`
(struct `TimerHal`, `sched-arch`-gated like the other HAL slices) over
the LAPIC timer wired in `kernel/arch/x86_64::preempt`.
`TimerHal::set_tick_callback` / `tick_callback` forward to the `preempt`
callback static, and `dispatch_tick` invokes it. Unlike the claim-based
ports, the x86_64 timer ISR must read the LAPIC ID from MMIO to derive
the firing CPU and issue the LAPIC EOI write — work with no host analogue
that `Timer::dispatch_tick` cannot express — so the ISR keeps its own
dispatch and `TimerHal` is the HAL-facing surface (callback install plus
the architecture-neutral dispatch the conformance vertical exercises).
The LAPIC LVT programming and EOI stay in `preempt` (§2.4). On the host
build, where there is no ISR, the handle backs the callback with an
in-handle cell solely for the `passes_timer_conformance` host test, which
runs `timer::conformance::run_all` over a real `TimerHal`.

## Context switch (`ContextSwitch`)

The x86_64 port implements the Arch HAL `ContextSwitch` slice
(`AGENTS.md` §17.2 / `plans/WIRING.md` Stage W5) in
`kernel/arch/x86_64::context_hal` (struct `ContextSwitchHal`) over the
bare-metal task-switch primitive in `kernel/arch/x86_64::context`
(`TaskCtx { rsp }` + `context.s`'s callee-saved save/restore).
`ContextSwitchHal::prepare` seeds a never-run task's first frame and
`switch` performs the ring-0 switch. The neutral `TaskContext` and the
port's `TaskCtx` are both a single `#[repr(C)]` `u64`, so the handle
reinterprets the pointer and forwards to `context` (a const-assert pins
the layout equality); the switch invoke lives in one place (§2.2). The
`context_hal` module is gated on `sched-arch` like the sibling
`timer_hal`/`percpu_hal` slices (that feature gates which HAL *modules*
compile); the `tairix-arch-api` dependency itself is no longer optional —
the always-compiled `paging` MMU slice (below) names it — so the feature
no longer pulls the dep. The underlying `context` primitive carries no
gate. The
`prepare` contract is host-tested via `context::conformance::run_all`
(`passes_context_switch_conformance`); the switch itself, like
`enter_user`, is proven only on the bare-metal target (the
`scheduler_stress` vertical drives the live scheduler), so it carries no
host check (§2.1 — no fake primitive).

## MMU / page-table (`AddressSpace`)

The x86_64 port implements the Arch HAL `AddressSpace` slice
(`AGENTS.md` §17.2 / `plans/WIRING.md` Stage W5b-1) on its
`kernel/arch/x86_64::paging::AddressSpace` (the four-level PML4 loaded
into `CR3`). `AddressSpace::map_page` translates the neutral `PageFlags`
into the leaf's writable/executable/user bits (forwarding a user page to
`map_4k_user_wx`, a kernel page to `map_4k`, one walk each, §2.2), guards
an already-mapped target with a read-only `leaf_present` walk (the
inherent `map_4k_inner` overwrites a PT leaf without checking), and fails
closed (`Misaligned`/`AlreadyMapped`/`PoolExhausted`/`InvalidFlags`).
`root_phys` returns the PML4 physical address and `activate` forwards to
the gated `switch` (the `CR3` load). Unlike the riscv64/aarch64 ports,
x86_64's walk recovers intermediate tables through the **higher-half**
kernel window (phys ≠ virt; `phys_of` subtracts `KERNEL_VMA_BASE`), so it
is **not** host-runnable — the `map_page`/`activate` path is therefore
gated to the bare-metal target and proven end-to-end by the
`memory_isolation` QEMU vertical (which now builds its victim/attacker
spaces through this trait), not a host conformance test. This is the same
honest asymmetry as the bare-metal `switch`, which the host also cannot
exercise (`AGENTS.md` §2.1). The `tairix-arch-api` dependency this slice
names is non-optional (the `paging` module is always compiled), unlike
the `sched-arch`-gated scheduler/timer/per-CPU HAL modules.

### Block split + guard-page fault-form (`plans/PI.md` G1/G2)

`AddressSpace::block_split_support` reports `BlockSplit::Supported`: the
x86_64 port re-expresses a coarse huge-page leaf at 4 KiB granularity, the
last `BlockSplit::Pending` port brought up to the aarch64/riscv64 level.
The inherent `split_block(vaddr)` walks PML4 → PDPT → PD and shatters
whichever huge leaf covers `vaddr`: a 1 GiB PDPTE huge page becomes a PD of
512 × 2 MiB huge pages (the page-size bit stays set — PD entries use it
too), then the 2 MiB PD huge page becomes a PT of 512 × 4 KiB pages with
the page-size bit **cleared** (at PT level bit 7 is the PAT attribute, not
page-size — Intel SDM Vol 3A §4.5). The shared `shatter_huge_into` helper
copies the leaf's `USER` / `NO_EXECUTE` bits onto every sub-entry and onto
the new table pointer, so the re-expressed region translates identically
with the same permissions (`AGENTS.md` §2.2 — one attribute decode). The
split only ever *adds* table levels reproducing the existing translation,
so it is break-before-make-free against the running regime, idempotent, and
fails closed (`Misaligned` / `NotMapped` / `PoolExhausted`). With it a
single 4 KiB page inside a former huge page tears down through the existing
`unmap` + `flush_page`. `prepare_guard_arena(base, len)` applies it to every
2 MiB block an arena spans (the G2 boot-mapping primitive).

Like the rest of the four-level walk this recovers intermediate tables by
their low physical address, so it is bare-metal-gated and proven by the
`tests/integration/stack_guard_qemu_x86_64` QEMU vertical, not a host
conformance test (`mmu::conformance::run_all`, which x86_64 does not run on
the host, only checks the `Supported` declaration, never exercising the
split — the positive proof is the vertical). The vertical boots the
production `tairix-kernel` pipeline (so the GDT, the dedicated
error-code-aware `#PF` entry, and the bump heap are installed) and, on
`BootCompleted`, builds a 4 GiB-identity space, activates it (`CR3`),
`split_block`s the 2 MiB huge page covering a dedicated guard static
(reached through its low-identity physical alias — distinct from the
higher-half RIP/stack that stay mapped), proves the split preserved the
mapping (sentinel write/read-back), then `unmap`s + `flush_page`s the single
guard page and reads it: the `fault` observer reports the supervisor
not-present `#PF` on exactly that page as PASS.

### Proving the overrun fault-form (`plans/PI.md` G3c)

G1/G2 prove a guard page can be unmapped and that a *direct* supervisor
access to it faults. G3c proves the **production runtime payoff** on
x86_64: that an *overrunning kthread* — a task whose execution runs off the
bottom of its usable kernel stack — takes a **synchronous, supervisor-mode
not-present `#PF` while it is running**, rather than the deferred
next-reschedule poison-canary detection a heap-backed
`tairix_kernel_core::BoxStack` falls back to (the §2.17 software defence
x86_64 keeps until the arena rewire lands).

`tests/integration/stack_overrun_qemu_x86_64` (the sibling of
`stack_overrun_qemu_aarch64`) boots the production `tairix-kernel` pipeline
and, on `BootCompleted`, builds a 4 GiB-identity space, activates it
(`CR3`), re-expresses a 2 MiB-aligned guard arena at 4 KiB granularity
(`prepare_guard_arena`), and `unmap`s + `flush_page`s one kthread stack's
one-page guard through the Arch HAL — exactly the production guard-page
mechanism. It then builds the live `tairix-kernel-sched-eevdf` `Scheduler`
over `X86_64Arch` and admits a kthread on that arena stack via
`spawn_kthread_with_stack` (the **production runtime path**, not a bare
function call), laid out `[guard page | usable stack]` on the arena's
low-identity alias. The kthread body overruns by touching the highest byte
of the (unmapped) guard region — the first byte a contiguous downward
overrun crosses — which raises the `#PF` on the still-healthy usable stack
above the guard (so the `#PF` entry does not nest-fault); the `fault`
observer confirms it is a supervisor not-present fault on exactly the guard
page and reports PASS. A regression that left the page mapped lets the body
return cleanly; the cooperative `step` loop then drains the task and the
test reports FAILURE explicitly rather than passing (`AGENTS.md` §2.9).
Enrolled in `tools/xtask/src/commands/qemu_tests.rs` (single CPU, 60 s).

This proves the *mechanism* end to end on x86_64; the **production** `init`
and runtime-`spawn` kernel stacks now run on the boot-reserved arena (the
G3b-2 rewire below).

### Routing the kthread stack through the arena (`plans/PI.md` G3b-2)

G3c proves the runtime fault-form on a hand-built arena; G3b-2 routes the
**production** PID 1 (`x86_64::init_spawn`) and runtime-`spawn`
(`x86_64::spawn_producer`) kernel stacks onto a boot-reserved guard arena, so
both run hardware-guarded rather than on the software-canary
`tairix_kernel_core::BoxStack`. This is the cross-port sibling of the aarch64
rewire (`docs/src/platform/aarch64.md`), reusing the **same**
`mem_map`/`stack_arena` infrastructure gated to `kernel_isa =
"aarch64"`/`"x86_64"` (one body, `AGENTS.md` §2.2).

The boot path carves the arena out of the **firmware** memory map rather
than laying out a single RAM window the way aarch64 does. After
`boot::build_memory_map` translates the loader's map,
`mem_map::carve_guard_arena_from_map(map, ram_bytes, max_addr)` walks the
usable regions for the first that can host a whole 2 MiB-aligned block of the
§24.2 policy size (`stack_arena_bytes`, ~1/64 of RAM, clamped to
`[2 MiB, 64 MiB]`) **below `max_addr`** — the 4 GiB identity window the spawn
seams build each task's root with, so the stack is reachable (and its guard
faultable) under the task's own `CR3` (`AGENTS.md` §4). It then
`reserve_range`s the block out of the usable map (the frame allocator never
hands those frames out) and the shared `boot::bring_up_bsp` `install`s it into
`KTHREAD_STACK_ARENA`. The decision is audited every boot (`EventId(4097)`,
`installed`/`base`/`len`); when no usable region fits a whole arena the carve
returns `None`, the install is skipped, and the seams fall back to the
software-canary `BoxStack` — fail closed, never fatal to boot (`AGENTS.md`
§2.9 / §2.17).

Each seam then allocates an `ArenaStack` from `KTHREAD_STACK_ARENA` (a
`FrameArenaGrow` chains fresh 2 MiB blocks out of the live `FrameAllocator`
on exhaustion, bounded to the identity window so the stack stays mapped) and,
on the task's **own** PML4, `split_block(guard)` + `unmap(guard)` re-expresses
the 2 MiB block covering the stack's guard page at 4 KiB granularity and
unmaps that single page. `init` does this **before** its `arch.switch()`; the
`spawn` producer does it on the child root it builds but **never switches to**
(the spawning caller keeps its own `CR3`) — so the split/unmap only walk the
child's tables through the caller's low-identity window, disturb no live
access, add only table levels reproducing the existing translation, and need
no TLB maintenance. A kernel-stack overrun then takes a synchronous,
supervisor-mode `#PF` under the task's own `CR3`. `publish_reclaim_frames`
gives the arena the live allocator so an exited task's `ArenaStack` returns
its idle chained blocks (grow *and* shrink, §24.1). Where no arena region is
available or the split/unmap fails, each seam falls back to `BoxStack` rather
than ever running on an unguarded stack.

The firmware carve is host-tested (`mem_map` unit tests: policy sizing,
base alignment up, skipping too-small and reserved regions, refusing a region
above and a block straddling the identity limit, and leaving the map
untouched on the no-arena path). The `spawn_init` / `spawn_session` /
`spawn_program` / `wait` / `stack_overrun` x86_64 `-M virt` verticals prove
`init` still spawns and supervises the session, and an overrun still faults,
now on the arena-backed stack.

## Cross-CPU TLB shootdown (`CrossCpuTlbShootdown`)

The x86_64 port implements the Arch HAL `CrossCpuTlbShootdown` slice
(`tairix_arch_api::xtlb`, `plans/WIRING.md` Stage W13) on `X86_64Arch`.
x86_64 has no broadcast TLB invalidation — `invlpg` touches only the
executing CPU — so this is the only port whose cross-CPU shootdown is
hand-written software. `kernel/arch/x86_64::tlb_shootdown` owns the
protocol: `shootdown_page` publishes the page and an outstanding-ack
count into a lock-serialised mailbox, raises a `TLB_SHOOTDOWN_VECTOR`
(`0x21`, one past the timer vector) IPI at every other online CPU, runs
`invlpg` locally, and spins until each target's ISR has run `invlpg`,
written its LAPIC EOI, and decremented the count. The local `invlpg` is
the one `TlbShootdown::flush_page` already uses (`AGENTS.md` §2.2). The
ack spin is genuine bounded synchronisation, not a "retry until it works"
hack — under-invalidating is the only failure mode, so the initiator must
wait — and deadlock is impossible because only the lock holder sends IPIs.
Each CPU installs the shootdown ISR through `init_local_tlb_shootdown` as
it comes online.

`tests/integration/cross_cpu_tlb_shootdown_qemu_x86_64` proves the
round-trip on a real second core: the BSP brings up an application
processor (via the `SecondaryBringup` HAL trait below), both install the
shootdown ISR, and the BSP drives `X86_64Arch::shootdown_page`, which
returns only once the AP's ISR has `invlpg`'d and acknowledged — so
reaching PASS proves the IPI + invalidation + ack executed on the AP.
Enrolled in `tools/xtask/src/commands/qemu_tests.rs` (`cpus: 2`, 60 s); a
single-CPU run correctly fails ("no application processor found"), so the
PASS is genuine.

## Secondary-CPU bring-up (`SecondaryBringup`)

The x86_64 port implements the Arch HAL `SecondaryBringup` slice
(`tairix_arch_api::smp`, `plans/WIRING.md` Stage W14) on `X86_64Arch`.
`start_secondary(cpu)` resolves the dense `CpuId` to its LAPIC id through
the handle's `cpu_to_lapic` map (failing closed with
`SmpError::InvalidCpu` for the boot CPU or an unmapped id) and delegates
to `kernel/arch/x86_64::smp::start_secondary`, which now owns the full AP
bring-up that previously lived in the QEMU test bin (`AGENTS.md` §2.2 —
no duplication): the per-AP 16 KiB stack pool, the `AP_TRAMPOLINE_PHYS`
frame view, the PIT-backed `Delay`, reading the boot `CR3`, stamping the
per-AP `ApBootSlot` with the set-once entry, the SDM INIT-SIPI-SIPI
handshake, and the wait on the AP's long-mode `ready` flag (so the shared
trampoline frame is safe to reuse for the next AP). The entry is installed
once via `smp::set_secondary_entry`; a missing entry is
`SmpError::NotReady` and a `ready`-flag timeout is `SmpError::StartRejected`.

The host `passes_secondary_bringup_conformance` test runs
`smp::conformance::run_all` over a real `X86_64Arch` (object-safe, fails
closed for an unstartable id, never panics); the real handshake is proven
end-to-end by `scheduler_stress_qemu` (BSP starts 3 APs through this
trait) and `cross_cpu_tlb_shootdown_qemu_x86_64`.

## Resumable ring-3 user kthread (`plans/PI.md` X1)

X1 brings the x86_64 port up to the aarch64 cooperative user-mode model:
a single ring-3 task admitted as a **resumable user kthread** that parks
and resumes under the live scheduler. It rests on two new primitives, the
x86_64 siblings of the aarch64 `activate_user_root`:

- `paging::activate_user_root(root_phys)` reloads `CR3` (the `mov cr3`
  primitive `AddressSpace::switch` already uses, factored to a free
  function taking only the root word so the per-task `pre_resume` hook
  stays `Send`). Loading `CR3` flushes the non-global TLB entries, so no
  explicit `invlpg` is needed. Host arm is inert; the real reload is proven
  by the QEMU vertical.
- `syscall_entry::set_kernel_rsp0(cpu, top)` repoints the per-CPU
  `SyscallTls.kernel_rsp0` slot (`gs:0`) at a value **without** rewriting
  `IA32_KERNEL_GS_BASE` or touching `user_rsp_save` — the per-resume
  counterpart of the boot-time `install_kernel_rsp0`. It applies the same
  fail-closed `validate_kernel_rsp0` stack-pivot check (non-null, 16-byte
  aligned, canonical, kernel half; `AGENTS.md` §3.5 / §5.4) before the
  write, so a hostile or buggy stack top is rejected rather than installed.

The reason x86_64 needs the second primitive is the asymmetry with
aarch64: an EL1 trap implicitly reuses the running kthread's `SP_EL1`, so
each aarch64 user kthread's `svc` lands on its own kernel stack for free.
On x86_64 the `syscall` entry stub loads the kernel stack from the
**per-CPU** `gs:0`, so the kernel must point it at the **current** user
kthread's own kernel stack on each resume, or two tasks' syscall handlers
would collide on one stack (a correctness *and* isolation defect,
`AGENTS.md` §4). The arch-neutral `kernel/core::kthread` `pre_resume` hook
therefore now receives the task's own kernel-stack top (`KernelStack::top`)
as an argument the dispatcher passes immediately before each switch-in;
aarch64 ignores it, x86_64 feeds it to `set_kernel_rsp0`. The durable
user-`%rsp` save lives on each task's own kernel-stack frame (see the X2
section below), so two tasks parking mid-handler never collide on it.

`tests/integration/spawn_el0_resume_qemu_x86_64` proves the round-trip. It
boots the production `tairix-kernel` pipeline (for the GDT user selectors,
the TSS, and `syscall`/`IA32_LSTAR` entry), and on `BootCompleted` enables
`IA32_EFER.NXE`, builds **one** hardware-isolated ring-3 address space from
the pure-Rust `tairix-test-el0-yielder` fixture through the
capability-checked, audited `kernel_core::spawn_image`, and admits it via
`spawn_user_kthread`. The task's `pre_resume` hook reloads `CR3` and
repoints the entry stack at its own kernel stack; the cooperative
`Scheduler::step` loop drives it, and the dispatch callback maps each
`yield`/`exit` to `reschedule_current`. PASS once the task yielded its full
build-pinned count and exited; a wrong drain count, an unexpected syscall,
or a stall fails loudly (`AGENTS.md` §7). Enrolled in
`tools/xtask/src/commands/qemu_tests.rs` (single CPU, 60 s).

## Two-task ring-3 timeshare (`plans/PI.md` X2)

X2 takes the X1 single-task model to **two** ring-3 tasks timesharing one
CPU, the cross-port sibling of the aarch64 SP2c timeshare. The moment two
resumable user kthreads park *mid-syscall-handler* and resume against one
CPU's per-CPU state, two x86_64-specific hazards appear that a single task
never exercises; X2 fixes both structurally.

**Durable user-`%rsp` save on the per-task kernel frame.** The X1 stub
stashed the user `%rsp` in the **shared** per-CPU `SyscallTls.user_rsp_save`
(`gs:8`) for the whole handler. If task A parks mid-handler and task B then
enters its own `syscall`, B's entry overwrites `gs:8` before A resumes, so A
would `sysretq` to B's user stack. The stub now `pushq %gs:8`s the
just-stashed user `%rsp` onto **A's own** kernel-stack frame (beside the
frame-resident saved RIP `%rcx`/RFLAGS `%r11`) and restores it with a single
`popq %rsp`. The user-`%rsp` slot doubles as the System V 16-byte alignment
pad the old stub already reserved, so the frame size — hence alignment — is
unchanged and there is no hot-path cost. `gs:8` is now a transient temp held
only between the entry `swapgs` and the first kernel-stack push, before any
cooperative switch can occur. This is the x86_64 analogue of the aarch64
`ELR_EL1`/`SPSR_EL1`/`SP_EL0` trap-frame save; structural, never a limit
bump (`AGENTS.md` §2.17).

**`swapgs` balance across a cooperative mid-handler park.** The durable-save
fix alone is necessary but not sufficient. Outside the entry stub's `swapgs`
window the kernel runs with current GS = user value and
`IA32_KERNEL_GS_BASE` = kernel TLS — the convention `enter_user`/`iretq`
relies on. When task A runs the entry `swapgs` (current GS now = kernel TLS)
and parks mid-handler via `reschedule_current`, the dispatcher enters task B
through `enter_user` (which does no `swapgs`), so B runs ring-3 with kernel
GS still active. B's first `syscall` `swapgs` then flips GS the *wrong* way →
`movq %gs:0,%rsp` reads address 0 → the next push faults on a null stack → a
`v=08` #DF with `rsp=0` at `syscall_entry_stub` (CR2=-8). X1 never exposes
this because the same task always performs the matching exit `swapgs`.

The fix is a HAL cooperative-park hook pair on
`tairix_arch_api::ContextSwitch` — `enter_cooperative_park` /
`leave_cooperative_park`, both default no-op (aarch64/riscv64 need nothing
here). `kernel/core`'s kthread runtime calls them in `suspend_thunk_syscall`
(the user-kthread mid-handler park path, reached only via
`reschedule_current`; a kernel kthread's `suspend_thunk_body` skips the
bracket — it never entered the convention), bracketing the suspend switch.
x86_64 implements them as a `swapgs` back to
the between-handler convention immediately before the park and a `swapgs`
back into the stub-window convention immediately after resume. Both `swapgs`
run on the *parking task's* own control flow and pair exactly; the first
trampoline→`enter_user` entry never goes through the syscall thunk, so it
correctly does no swapgs, and an `Exit` park (which never resumes) correctly
leaves the CPU in the between-handler convention the dispatcher expects. The
hook is structural and fail-closed; it adds no authority (capability checks
stay kernel-side, §5.4) and does not weaken per-PML4 isolation (§4). No ABI
change.

`tests/integration/spawn_el0_timeshare_qemu_x86_64` proves it. It boots the
production `tairix-kernel` pipeline and, on `BootCompleted`, enables
`IA32_EFER.NXE`, builds **two** hardware-isolated ring-3 address spaces (two
PML4s drawing from one shared frame pool, §4) from the pure-Rust
`tairix-test-el0-yielder` fixture through the capability-checked, audited
`kernel_core::spawn_image`, and admits each as a resumable user kthread whose
`pre_resume` hook reloads its `CR3` and repoints the per-CPU entry stack at
its own kernel stack. The cooperative `Scheduler::step` loop drives both; the
dispatch callback maps each task's `yield`/`exit` to `reschedule_current`, so
the two ping-pong through real ring-3↔kernel context switches. PASS once both
yielded their full build-pinned count and exited; a wrong drain count, an
unexpected syscall, or a stall fails loudly (`AGENTS.md` §7). Enrolled in
`tools/xtask/src/commands/qemu_tests.rs` (single CPU, 60 s).

## PID 1 (`init`) reaches ring 3 (`plans/PI.md` X3a)

X1/X2 proved the cooperative user-mode model with *test-driven* ad-hoc
schedulers. X3a brings the **production** x86_64 boot pipeline up to the
aarch64 P6c-3 milestone: the real `kernel_main` + `InitSpawn` path spawns
PID 1 (`init`) into ring 3, and `init` writes its banner over its inherited
standard output. It is the prerequisite for the x86_64 runtime `spawn`
producer (X3b).

Three pieces, all wired into the production `tairix_kernel::boot`:

- **The COM1 console backing.** `serial_sink::Com1Console` implements
  `kernel_core::ConsoleWrite` over the same COM1 16550 the log sink uses, so
  the `stream_write` syscall on fd 1/2/3 reaches the serial line. It is the
  x86_64 counterpart of the aarch64 `UartConsole` — a stream *backing*, not a
  program-facing device (`AGENTS.md` §20). Listed as the only entry of the
  `BootInfo::with_consoles` console list, with the fail-closed
  `NULL_CONSOLE_READ` as its read half (no COM1 RX drain is wired on this
  slice).
- **`IA32_EFER.NXE`.** The shared `boot::bring_up_bsp` enables the No-Execute-Enable bit
  on the BSP before any user image is built, so the W^X No-Execute leaf bit
  the process-image builder sets on a program's data/rodata and stack pages is
  honoured rather than faulting the page-table walk (`AGENTS.md` §19.2). The
  X1/X2 verticals enabled it themselves; it is now a production CPU-setup step.
- **The PID 1 spawn seam.** `x86_64::init_spawn::X86_64InitSpawn` implements
  `kernel_core::InitSpawn` (installed via `BootInfo::with_init`). After
  `BootCompleted`, `kernel_main` invokes it: it builds `init`'s ring-3 image
  through the capability-checked, audited `kernel_core::spawn_image` and admits
  it as a resumable user kthread (`InitSpawnCtx::admit_init`), then drains the
  run queue. Its `pre_resume` hook reloads `CR3` (`activate_user_root`) and
  repoints the per-CPU entry stack (`set_kernel_rsp0`), exactly like X1. PID
  1's kernel stack is drawn from the boot-reserved kthread guard arena
  (`KTHREAD_STACK_ARENA`): the seam allocates an `ArenaStack` and unmaps its
  guard page in PID 1's own PML4 before `arch.switch()`, so a kernel-stack
  overrun faults synchronously under PID 1's `CR3` (the G3b-2 rewire above),
  falling back to the software-canary `BoxStack` only when no arena was
  carved.

**Why the init space needs a gigabyte-scale identity map.** The seam switches
`CR3` to the fresh per-process space while it builds the image (the
`admit_init` contract requires the image be built into the *active* space).
The x86_64 page-table walk (`ensure_child`) recovers each intermediate table
from its **low physical address**, i.e. it assumes the table frames are
identity-mapped; and the live frame allocator hands the image's frames out of
physical RAM past the low 32 MiB. So the minimal `new_identity_first_32mib`
window the X1/X2 verticals use (whose frame/table statics happen to live in
low memory) is insufficient here — the walk #PFs the moment it dereferences a
table or frame above 32 MiB. The new `paging::AddressSpace::new_identity_first_gib`
(a shared `new_identity` helper also backing `new_identity_first_32mib`)
identity-maps whole gigabytes with 2 MiB huge pages; the seam maps 4 GiB,
mirroring the boot trampoline's identity map, which covers all of RAM and the
LAPIC MMIO page the scheduler touches under PID 1's `CR3`. Physical frames are
written through a `DirectPhysMap` over the `[0, 1 GiB)` higher-half window, so
the QEMU box's RAM is reachable; wider physical RAM is a later direct-map stage
shared with the rest of the port.

`tests/integration/spawn_init_qemu_x86_64` proves it. It reuses the entire
production pipeline (only the audit sink is replaced) and reports PASS once it
observes `ProcessSpawned` (the image was built) and an audited `SyscallInvoked`
(PID 1's `exit`, reached after its gated banner write landed). A bad image, an
entry fault, or an unhandled first `syscall` never emits the audited syscall, so
the run times out (fail-loud, `AGENTS.md` §7). Enrolled in
`tools/xtask/src/commands/qemu_tests.rs` (single CPU, 60 s).

## Runtime `spawn` concurrent producer (`plans/PI.md` X3b)

X3a dropped PID 1 into ring 3 but left its session launch failing closed
(`NULL_PROCESS_SPAWN` → `NotImplemented`). X3b adds the real x86_64
`ProcessSpawn` producer — `x86_64::spawn_producer::X86_64ProcessSpawn`,
installed into the production `tairix_kernel::boot` hand-off through
`BootInfo::with_spawn` beside the X3a `with_init` seam — so a task holding
`CAP_PROC_SPAWN` (PID 1 `init`) can launch a **second, hardware-isolated,
concurrently-runnable** process. It is the cross-port sibling of the aarch64
`spawn_producer` (`plans/SPAWN.md` SP3b).

When `init` issues the `spawn` syscall for its session (the login service
`/System/Services/login.app/Run`, `plans/PI.md` P11; login in turn spawns the
authenticated record's shell, `/System/Apps/elsh.app/Run`), the kernel resolves
the path against the embedded `spawn_layout::PROGRAM_REGISTRY` (whose `rxe`s
`build.rs` bakes, exactly like PID 1's `init` image) and hands the matched
program to the producer, which:

- draws the child's page-table frames from the kernel's live `FrameAllocator`
  through a `FrameTableSource` (no fixed `.bss` pool, so the spawn capacity
  scales with discovered RAM; fail-closed `NoSpace` on genuine exhaustion,
  `AGENTS.md` §24.1 / §2.9), builds a 4 GiB-identity child PML4 with
  `new_identity_first_gib`, and captures its root;
- drives the capability-checked, audited `kernel_core::spawn_image` (emitting
  `ProcessSpawned`) to populate the child's segments/stack/startup block, then
  admits it **Ready** through `SpawnCtx::admit_process` — returning the child's
  PID without entering it (a true concurrent spawn, not an `exec`-style
  hand-off, `AGENTS.md` §4). The child receives only its registered
  program's declared capability set (the shell: the console pair; login
  additionally `CAP_PROC_SPAWN` + `CAP_USERS_READ`), never the spawning
  caller's authority (`AGENTS.md` §4, §5.2, §16.5);
- gives the child an arena-backed, hardware-guarded kernel stack — an
  `ArenaStack` from `KTHREAD_STACK_ARENA` whose guard page the producer unmaps
  in the child's own (inactive) PML4 (the G3b-2 rewire above), falling back to
  a software-canary `BoxStack` only when no arena region is available — and a
  `pre_resume` hook that reloads `CR3` (`activate_user_root`) and repoints the
  per-CPU entry stack (`set_kernel_rsp0`) before each switch in, exactly like
  X1/X3a.

**Building the child without switching `CR3`.** Unlike the X3a PID 1 seam — which
switches `CR3` to the fresh space to build PID 1's image — the runtime producer
runs *under PID 1's own `CR3`*, which `new_identity_first_gib` built to
identity-map the low 4 GiB **and** mirror the higher-half kernel window. The
page-table walk recovers existing tables by low physical address (identity), new
tables through their higher-half static pointer, and the image content through a
higher-half `DirectPhysMap` — all mapped under PID 1's active root (the child's
page-table frames come from the live allocator in the low window). So
the producer builds the child's tables through the caller's active `CR3`,
never switching it, so the running parent is never moved out from under itself —
exactly as the aarch64 producer builds through its identity window
(`AGENTS.md` §2.2). The child's own `CR3` is reloaded by its `pre_resume` hook
before the scheduler first resumes it.

`tests/integration/spawn_session_qemu_x86_64` proves it, end to end through the
full supervision cycle. It reuses the entire production pipeline (only the audit
sink is replaced): after `BootCompleted`, `kernel_main` builds PID 1
(`ProcessSpawned` #1), `init` writes its gated banner and `spawn`s the session,
the producer builds it a fresh isolated PML4 (`ProcessSpawned` #2) and admits it
Ready, the cooperative drain runs the session in its own ring-3 space until it
`exit`s, then `init`'s `wait` reaps it, returns to ring 3, and **relaunches** the
session (`ProcessSpawned` #3). PASS once **three** `ProcessSpawned` and **four**
audited `SyscallInvoked` are observed (`init`'s `spawn`, the session's `exit`,
`init`'s `wait`, and `init`'s relaunch `spawn`), proving the whole
`wait`→reap→relaunch supervision cycle ran — the cross-port equal of the aarch64
`spawn_session_qemu_aarch64`. A regression that never builds, runs, reaps, or
relaunches the session never reaches the threshold, so the run times out
(fail-loud, `AGENTS.md` §7). Enrolled in
`tools/xtask/src/commands/qemu_tests.rs` (single CPU, 60 s).

## `wait`: blocking reap of a child on x86_64 (`plans/PI.md` X4)

The `KernelProcessWait` producer (the `wait` syscall's scheduler-side seam) is
installed on every production pipeline by `kernel/core`'s `run_phases`, so
`register_child` (on the spawn-admit path) and `record_exit` (in the `exit`
handler) already fire on x86_64. X4 adds the proving vertical,
`tests/integration/wait_qemu_x86_64` — the cross-port sibling of
`wait_qemu_aarch64`.

It boots the production `tairix-kernel` pipeline (so the GDT ring-3 selectors,
the TSS, and `syscall`/`IA32_LSTAR` entry are installed) and, on
`AuditEvent::BootCompleted`, builds a **parent** and a **child** hardware-isolated
ring-3 address space (two PML4s, one shared frame pool) from the cross-arch
`wait_program` fixture — compiled twice, once per role, and converted to `rxe`.
It installs a `KernelProcessWait<X86_64Arch>`, records the parent/child link,
admits both as resumable user kthreads, and drives the cooperative
`Scheduler::step` loop; the dispatch callback routes the child's `exit` and the
parent's `wait`/`exit` through the producer + `reschedule_current`.

It admits the **parent first**, so the cooperative loop dispatches the parent
before the child: the parent's `wait` runs while the child is still
registered-but-unexited, forcing the producer to **park** the parent
(`Reap::Blocked` → `reschedule_current(Yield)`) rather than reap it immediately.
The child then runs and `exit`s; the parent is re-dispatched, its `wait`
re-polls and reaps the zombie, the kernel copies the reaped exit code out to the
parent's `status` pointer (through the parent's frozen address space), and the
parent verifies the agreed code and exits 0. This is the
**resume-after-cooperative-park** return-state path on the x86_64 trap: the
parent suspends mid-`wait`-handler and resumes on its own kernel-stack frame,
restoring its saved user `%rsp` and balancing `swapgs` (the X1/X2 fixes), then
`sysret`s back to ring 3. PASS once the parent reaped the child, read back the
code, and exited 0; a wrong code, a missing reap, an unexpected syscall, or a
stall fails loudly (`AGENTS.md` §7). Enrolled in
`tools/xtask/src/commands/qemu_tests.rs` (single CPU, 60 s).

### Reserving the kernel image out of usable RAM

The runtime `spawn` producer and the `wait` reap/relaunch cycle both lean on the
frame allocator (`kernel_mem::FrameAllocator`), which it builds from the loader
memory map `boot::build_memory_map` assembles — the UEFI map on a GRUB-EFI
boot (where `bootmemory::from_uefi` classifies `EfiLoaderCode`,
`EfiLoaderData`, `EfiBootServicesCode`/`Data`, and `EfiConventionalMemory`
all as `Usable`, correct after `ExitBootServices`), or the PVH/E820 map on a
QEMU direct boot (plain RAM). Either way the loader places *this* kernel
inside memory that map reports usable, so the running kernel's code and bump
heap sit inside a `Usable` region.

Without a carve-out the allocator eventually hands out frames overlapping the
live kernel: by the second (relaunch) `spawn`, the low usable RAM consumed by
boot + PID 1 + the first session pushes the cursor across 1 MiB into the kernel
image, and the `spawn` image builder's zero-fill / page-table writes (through the
higher-half direct map) corrupt live `.text`, derailing the kernel into wild
execution. This was the X4 follow-on defect.

The fix is the x86_64 sibling of the aarch64 `mem_map` `[ram_base,
__kernel_end)` reservation: `build_memory_map` reserves the whole kernel image —
`[__boot_phys_start, __kernel_phys_end)`, the boot trampoline at 1 MiB through
the end of `.bss` (which includes the bump heap) — out of the usable RAM via
`BootMemoryMap::reserve_range`, which clips the range out of every `Usable`
region (leaving it an implicit reserved gap the allocator never marks free). The
`__kernel_phys_end` symbol is emitted by `kernel/arch/x86_64/linker.ld` as a
physical address (`. - KERNEL_VMA_BASE`). With the kernel image reserved, the
allocator can never hand out a frame inside it, and `spawn_session_qemu_x86_64`
runs the full supervision cycle (3 `ProcessSpawned` / 4 audited syscalls). The
`reserve_range` clip + the allocator-never-hands-out-a-reserved-frame contract
are host-tested in `kernel/mem/src/bootinfo.rs`.

## A2 — production boot storage floor + root-unlock admission

`plans/ARCHSUPPORT.md` A2: the x86_64 production boot now composes the same
encrypted-root → `/System` mount → app store → users DB pipeline the
aarch64/riscv64 boots do, over the discovered virtio-blk-PCI disk. The boot
composition is landed and host-gate-green; the whole-disk image builder (A1)
and the live QEMU verticals are staged separately, exactly as the riscv64
parity port was brought up host-gate-green before its boot-confirmed
vertical.

`boot::seed_hardware_tree` returns the leaked `&'static [HwNode]` tree it
publishes to `HW_TREE`. `boot::try_boot` resolves the bootstrap root block
binding from that tree through the shared
`root_storage::resolve_root_block_driver` gate (the same `lib/devmatch`
policy `devmgr` uses) and stashes it with
`unlock_service::record_boot(binding, /* dtb */ 0, tree)` — the DTB pointer
is `0` because the x86_64 bring-up re-resolves the virtio transport from PCI
configuration space, not a firmware device tree. `try_boot` then wires
`with_app_store` / `with_users_db` / `with_users_admin` / `with_filesystem` /
`with_volumes` / `with_volume_service` exactly as the other ports do.

The port's unlock admission is `x86_64::root_unlock`. At the PID 1 spawn seam
(`x86_64::init_spawn`, before `admit_init`) `spawn_if_present` admits an
in-kernel kthread that brings the bound virtio-blk-PCI root up in
`virtio_blk_unlock`: it builds the PCI bus over `tairix_pci::mechanism_one`
(port-I/O configuration mechanism #1), provisions the four virtio
configuration windows into a `PciTransport` through the `CAP_MMIO_MAP`-gated
`KernelMmioMapper`, and routes the device's interrupt through **MSI-X** —
binding the function's *discovered* PCI Interrupt-Line GSI (configuration
offset `0x3C`, never a board constant), reusing the vector the boot pipeline
assigned that GSI, and programming the MSI message into the device's MSI-X
table. Because MSI-X delivers the vector straight to the LAPIC, no IO-APIC
redirection entry is on the delivery path; the shared `IrqParkWaiter`'s
mask/rearm of the pin is harmless. The DMA host draws from the kernel's live
frame allocator over a `DirectPhysMap::identity` window, and the opened
`VirtioBlk` is handed to the shared `unlock_orchestrate::finish_unlock` tail
(the interactive unlock task + the persistent driver-store serve loop). The
console-0 read half is the fail-closed `NULL_CONSOLE_READ` this slice
(interactive COM1 input is A3), so `login` fails closed while the disk still
mounts and the driver store still serves the user-space autoload.
